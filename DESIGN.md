# Design System: Supervisor

## Overview

**Creative North Star: "Transport Interchange Wayfinding"**

Transport interchange wayfinding gives Supervisor a stable midnight-indigo navigation field and clear work surfaces. Teal marks the selected route; action blue identifies links, controls and keyboard focus. The personality comes from aligned information, restrained geometry and readable operational type.

The workspace is compact without compressing the meaning of work. A task statement, semantic outcome, connected workflow and actual plan alignment each have a distinct reading role. Native activity, Supervisor assessment and agreement remain separate facts. Borders and tonal insets organize detail; narrow containers stack the same content and follow the system color preference. This is an extension of the existing Operate system, with the existing application mark and source assets unchanged.

**Key Characteristics:**

- A persistent indigo navigation field beside a quiet work canvas.
- Aligned rows and explicit text labels for state, scope and freshness.
- Connected, collapsible workflow branches with a named current step.
- A separate agreement region and clearly disclosed retained history.
- Blue actions, teal selection and semantic amber/red attention.
- Flat bordered surfaces, modest corners and minimal motion.

This record is extracted from the current local UI source, with retained fixture captures as supporting visual evidence. The surface direction contract owns the page strategy and online pattern references. No new visual-world seed was rolled for this extension; the inherited seed is not verified provenance, and no approved raster comp or new raster is involved. Shared review paths can be overwritten by later recaptures; this document does not establish their freshness, installed behavior or deployment status.

## Colors

The palette combines a cool neutral workspace with an indigo navigation field, blue actions, teal selection and explicit state colors. Frontmatter holds exact values; base names are the light scheme and matching `dark-` names are the implemented dark overrides.

### Primary

- **Action blue** (`blue`, `dark-blue`): links, caret, control hover borders and work-area focus. The dark link/focus blue is lighter than the filled primary control.
- **Primary control** (`blue`, `dark-button-primary`): filled actions with `on-accent` text. `blue-hover` is the implemented primary hover fill in both schemes.

### Secondary

- **Route teal** (`teal`, `dark-teal`): selected project-tab underline, quiet-state icon and assessed journey markers.
- **Selected conversation view** (`section-selected` / `section-selected-ink`, with dark counterparts): a tonal fill with stronger teal text.
- **Rail selection** (`rail-selected`, `rail-active-icon`): a lighter indigo fill, white text and pale-teal line icon. `rail-hover` and `rail-focus` complete the interaction states.

### Tertiary

These are semantic state pairs, not decorative accents. Each `status-<name>-bg` / `status-<name>-ink` pair has a dark counterpart.

- **Blue:** informational and underway records.
- **Green:** enabled, valid or completed records, according to the accompanying label.
- **Amber:** attention, incomplete reads or uncertain conditions.
- **Critical red:** blocked or failed states. `invalid` and `dark-invalid` supply invalid-input borders.
- **Native active green** (`native-active`): the connected/active dot, accompanied by its native-state text. This value stays the same in both schemes.
- **Current journey** (`journey-current-bg`, `journey-current-label-bg`, `journey-current-ring`): a quiet teal row, stronger state label and marker outline. In dark mode the row uses `dark-status-green-bg`, the label uses the dark selected-view pair and the outline uses `dark-journey-current-ring`. These are intentional state colors.
- **Journey attention boundary** (`journey-attention-line`): the amber marker outline, with the existing amber state pair inside. Dark mode uses the dark amber foreground for the outline.
- **Disable action boundary** (`danger-line`, `dark-danger-line`): a restrained red outline around an explicit disable action. Text and hover fill reuse the critical state pairs.

The outcome strip deliberately shares green tint for work underway and completed work; the title, explanation and marker distinguish those meanings. A green proposal-prepared marker in the agreement panel describes a recorded planning action, not completed execution.

### Neutral

- **Ink** and **quiet**: primary work text and secondary explanatory text.
- **Surface**, **soft** and **canvas**: white work areas, cool tonal insets and the surrounding pale workspace; dark counterparts preserve their separation with blue-black tones.
- **Line** and **control line**: quiet content boundaries and stronger interactive-control outlines.
- **Rail** and **rail quiet**: midnight-indigo navigation and its subdued blue-white labels. The rail darkens in dark mode; quiet text and the selected fill retain their base values.

**The Accent Roles Rule.** Use action blue for links, controls and work-area focus. Use teal for selected project routes and conversation views; the indigo rail keeps its own selected fill and pale-teal icon.

**The State Needs Words Rule.** Pair every status color or activity dot with text. Amber and red describe an actual issue, state or explicit disable action; native activity remains separate from supervision and assessment.

Browser text selection uses a pale-teal background and dark ink; scrollbars use the control outline against the tonal inset. Carets and focus share action blue. These treatments extend the palette into native browser surfaces.

## Typography

**Body and operational heading font:** the platform sans stack in frontmatter. There is no separate reusable display face.

**Label/Mono font:** labels use the same sans; literal code, paths and identifiers use the recorded monospace stack.

**Character:** precise, familiar and compact. Weight and small changes of scale establish hierarchy without ornamental lettering.

### Hierarchy

- **Headline:** page headings with tight tracking and compact line height; the mobile role replaces the desktop size at the narrow breakpoint.
- **Title:** major sections, with a slightly smaller mobile size.
- **Section:** subordinate headings and fieldset legends.
- **Objective:** the task statement uses the recorded fluid clamp, weight (650), line height (1.35) and a wide measure (92ch), so a long statement stays within three lines on a desktop task view.
- **Journey heading / workflow title:** plan-progress section headings and the titles inside workflow surfaces.
- **Context title:** alignment, observation and compact definition headings.
- **Outcome:** the semantic result title; the guide introduction shares its scale with regular body weight and line height.
- **Health summary:** the leading explanation in conversation Supervision.
- **Detail / reading:** step explanations, alignment messages and freshness metadata. Speaker labels and assessment labels use their separately recorded bold weights; breadcrumbs stay quiet.
- **Step state:** compact, semibold text alongside each journey stop.
- **Body:** default work content. Measured line limits vary by purpose: page descriptions (72ch), work objectives (64ch), focused objectives (64ch), empty-state explanations (65ch), guide content (82ch) and source definitions (85ch).
- **Label:** buttons and concise form labels. The recorded label line height is the button value; ordinary labels inherit body line height.
- **Navigation:** project and conversation links; current items increase weight to (600).
- **Caption:** read times and supporting information.
- **Badge:** compact sentence-case status text.
- **Input:** readable field text; weight follows the surrounding control or label.
- **Code:** relative sizing follows surrounding text, with local sizing for excerpts.

**The Operational Type Rule.** Use the platform sans for work content, labels and operational headings. Reserve monospace for source, paths and identifiers; status labels stay in sentence case.

## Layout

The instance header reduces to a minimum height of (62px), the workspace uses (25px 18px), and ordinary panel padding becomes (19px). The task statement stays unboxed. ## Elevation & Depth

Depth comes from borders and tonal surfaces. Content panels have one (1px) boundary; nested panels flatten into a top rule and vertical spacing. The navigation field, work surfaces and cool insets establish the layers. There are no authored box shadows. A modal uses the existing translucent indigo backdrop and a bounded, scrollable surface without adding a shadow vocabulary.

**The Single Boundary Rule.** Give a work surface one quiet border. Inside an existing panel, separate sections with rules and spacing instead of another rounded card.

Motion is limited to a border-color transition (140ms, ease-out) on buttons and links and background/border transitions (180ms, ease-out) on journey markers when reduced motion is not requested. The active marker outline is a state cue, not an elevation shadow. Hover changes fill and border without a lift or entrance effect. Reduced-motion mode retains automatic scrolling.

## Shapes

Surfaces are gently rounded rectangles with crisp, quiet borders. Frontmatter records observed steps for status tags, controls, rail items, contextual insets, work surfaces and dialogs. Tags are compact rounded rectangles rather than full capsules; activity dots and ordinary journey markers are circular. The attention marker intentionally changes to a small rounded square using `attention-mark` (6px); workflow disclosures and retained-history wrappers use the contextual radius (9px). The filter toolbar and table form one shared rounded enclosure.

Icons are authored SVG line drawings on a (24 × 24) view box, with no fill, a (1.7) stroke and rounded caps/joins. Default rendered size is (20px), with smaller (16–18px) instances beside text. Decorative SVGs are hidden from assistive technology. The existing PNG application mark appears at (36px) in the desktop rail and (32px) on mobile.

## Components

### Buttons

Compact, explicit actions. Primary, bordered secondary and quiet variants share the control radius and recorded padding. Hover changes the border to action blue and the neutral fill to the tonal inset; primary hover uses its deeper fill. Quiet buttons remove their resting border and fill, then receive the standard neutral hover. Disabled buttons reduce opacity to (0.55) and use a default cursor. The global keyboard outline is (3px) with a (3px) offset. Busy states retain an action label such as “Saving…”. Explicit disable actions use the documented danger text and boundary, with a critical-tinted hover; Reload status stays a separate quiet action.

### Chips

Small textual state markers. Neutral chips use the tonal inset and quiet text; blue, green, amber and critical variants use their recorded foreground/background pairs. Labels explain the color in sentence case. Counts use tabular numerals.

### Cards / Containers

Flat work surfaces. Ordinary panels use the surface radius, quiet border and recorded padding. Nested sections flatten into rules. Project directories and conversation lists use aligned rows with separators and clear linked titles. Empty states use a dashed control outline; loading states use static tonal bars.

### Inputs / Fields

Familiar native controls with a stronger outline than content containers. Inputs, selects and textareas share the control radius, surface fill and recorded inset. Placeholders use quiet ink at full opacity; the caret uses action blue. Invalid fields use the semantic invalid border. Textareas resize vertically and start at a minimum height of (116px). Focus uses the common visible outline; native disabled and fieldset behavior remains intact.

### Navigation

The rail pairs a label and line icon; current selection adds the selected indigo fill, white text and teal icon. Rail keyboard focus uses its pale-teal outline. An amber count marks recorded attention items. Mobile keeps the same four destinations in a top grid.

Project pages use a restrained bottom boundary and teal current-item underline (2px); a project opens at Conversations. Inside a conversation, linked Projects and project breadcrumbs lead back to scope, and the title band carries the conversation title, its two views (Task, Supervision) and Open in T3. The project tab row is hidden there. Conversation links use a tonal teal selected fill and wrap without splitting their labels. Checkout selection appears only in Definitions. Current state belongs to the active link through `aria-current`; Guide is a separate reference link in its own navigation landmark. Moving to another page, project or conversation, including through Back and Forward, focuses that view's visible h1; switching between a conversation's views keeps focus on the activated link.

### Attention and notices

The Task status includes the server's typed conversation mode and availability.
“Following the conversation” uses existing quiet text only for current eligible
supervision; updating, stale, uncertain, stopped and unavailable states have explicit
text. Engaged mode composes the existing agreement and execution treatment. The
native “Understanding and draft duties” disclosure keeps the evolving draft separate
from acceptance and evidence. Background updates preserve focus; meaningful status
changes use a polite live region, while interstitial catching-up updates remain silent.

Attention rows keep title, reason and context together in an amber-bordered list. Hover uses a warmer surface; dark mode supplies its own border and hover colors. Quiet states use a teal-tinted inset and explanatory label. Informational and draft notices use blue-tinted backgrounds and boundaries. These treatments describe actual records or uncertainty.

### Task meaning and outcome

The task statement leads on the canvas without a surrounding card. A tonal outcome strip names work in progress, task completion, attention or stopped supervision, with its marker and the assessment explanation. When a current task-bound assessment exists, the strip can list underway or attention steps after “Now:”. A stopped state suppresses that current-step line. One metadata line follows: the agreement state, the assessment time (or an honest reading state such as Reading, Unavailable or Coverage incomplete), the read time and the view's one Refresh. Attention reasons that the outcome, agreement panel or a record's own details already state are not repeated in the attention band. No percentage or remaining-effort estimate is inferred from step counts.

### Connected workflow journey

The bordered plan surface carries the full recorded topology. Sequences use ordered lists and connected tracks; parallel groups use unordered lists, a named “In parallel” region and a dashed side boundary, explicitly saying that branches have no declared order. Nested workflows retain their own boundary and status, with nested contents inside the workflow disclosure. A child's completion never changes its parent's assessment by implication.

Each stop is a native disclosure with an SVG state marker, name, textual state and chevron. Live underway and attention items open initially, along with ancestor workflows needed to reveal them. Other completed and planned items start collapsed; an ancestor keeps its own recorded state. The underway summary carries `aria-current="step"`. Statuses come only from the current workflow bound to the task; before one exists, the journey shows the proposal with dashed “Proposed” markers or the accepted plan labelled “Accepted” and “Not yet assessed”, and historical snapshots use “In earlier plan”. Those non-live contexts never inherit execution status, and a pending proposal never replaces or merges into the current workflow. A workflow without an expanded plan says so explicitly.

The disclosure holds the step's duty (definition description), read-only references and skills, its Plan note, and, matched by occurrence ID within the same task, an Accepted plan note and a “Proposed plan note · awaiting acceptance” when they differ. A Supervisor assessment appears only from that step's own recorded status change, with its transition and time; other step records sit in an Earlier step records disclosure. A workflow lists its not-applicable original commitments with their reasons. A quiet source line names the definition or task-local ID and path. Steps affected by a pending update carry an “Update proposed” chip; a live step missing from the accepted plan carries “Not in the accepted plan”. The current step gains the documented teal row, label and ring; completion adds a check; attention adds the amber square marker. The plan can show assessed-complete counts, without turning those counts into task completion.

**The Topology Before Totals Rule.** Preserve sequence, parallel and nested workflow boundaries, and keep parent assessment independent from child completion.

### Alignment and agreement

The tinted Agent and Supervisor region beside the plan presents the actual proposal state and the recorded agent acceptance as two attributed rows, each message stated once: a proposal's message only while it is the open question, the acceptance message once accepted. Messages come from those records; they are not invented chat. Links open the Supervisor and agent conversations. Disclosures hold the acceptance record (time, proposal, agent and Supervisor message or interpretation submission), plan provenance (proposal status, definitions status, requirements, checkout and revision, issues) and the task interpretation. “Plan accepted” requires an active task whose acceptance covers the current proposal. A revised proposal reads “Earlier plan accepted; update awaiting acceptance”, without implying an enforcement gate, and a “Proposed update awaiting acceptance” panel lists the actual added, removed and changed steps against the accepted plan, with an optional plan-note comparison.

**The Current Task Rule.** Bind current outcome and alignment to the selected task; retain unrelated workflow records as explicitly labeled history without presenting their agreement as the current task's agreement.

### Evidence and history

One “Evidence and history” disclosure follows the plan. It holds every Supervisor record (newest first, with its step, transition, time and source references), external contributions for steps no longer in the plan, the native conversation lifecycle with supporting activity, an out-of-date earlier acceptance with its plan in historical labels, and an unlinked earlier workflow in a dashed “Earlier workflow” disclosure with a retained-record notice and no current-task agreement panel. It never repeats the current plan. Connected work (child conversations, their workflows and assignments) appears only when such work exists.

## Do's and Don'ts

### Do:

- Do preserve the indigo navigation field and the distinction between canvas, work surface and tonal inset in both color schemes.
- Do keep state labels, native activity, read times and uncertainty readable together.
- Do preserve full workflow topology, explicit proposal/agreed/historical contexts and the distinction between current-task alignment and retained history.
- Do lead with task meaning and a named semantic outcome before exposing provenance.
- Do use visible keyboard focus, labeled controls and the existing narrow-screen reflow.
- Do draw icons as consistent stroked SVG and keep monospace for literal technical content.

### Don't:

- Don't use amber or red as decoration, or let a color alone communicate status.
- Don't add decorative shadows, gradients or nested rounded cards to the flat work surfaces.
- Don't infer completed work from an accepted plan, a completed child, quiet native activity or an assessed-step count.
- Don't repeat project navigation inside the conversation navigation or expose checkout selection outside Definitions.
- Don't reuse the sign-in display scale for workspace labels.
