# Configurable supervisor guidance

Status: proposal, not activated. The adjacent `intent-monitor.html` is an interactive, disconnected prototype. Its examples, model decisions and delivery records are fixtures; no chat is read or messaged.

## Outcome

One continuously running supervisor observes T3 activity, decides whether a user-configured situation is present, and sends the configured guidance to that same chat. One supervisor-owned UI manages rules and explains all supervisor activity, including existing recaps and Telegram handling. Everything lives in `t3-supervisor`; T3 source remains untouched.

This is advisory monitoring. It may miss an intent, misunderstand it, or send after an action. A delivered message is not proof that the worker followed it. It is not a mandatory pre-publication gate.

## Configuration that reads like an instruction

A rule has a name, **When to notice**, **What to tell the chat**, a scope and a mode. Both main fields accept ordinary human language. No regex, command names, generated code or compulsory keyword prefilter is required.

Example global rule:

- **When:** The working agent expresses a current intention to publish a non-draft pull request. Ignore draft creation, quoted examples, hypothetical plans and negated intentions.
- **Tell:** Before publishing, obtain the requested independent adversarial review and resolve concrete findings. If the review already covers the current commit, cite that evidence and continue; do not repeat it unnecessarily.

This example notices an expressed publishing intention. It avoids claiming that an earlier or external review never happened. A custom condition such as “publish without review” can be indeterminate when the monitor cannot see the relevant review; the result must be **Needs context**, not an invented failure.

Optional examples help refine a condition. The supervisor may suggest clearer wording, but never silently rewrite a rule or add inferred requirements. Positive and negative test examples are encouraged, not a second programming language or a mandatory approval ceremony.

## Scope and availability

The first implementation observes one explicitly connected T3 environment. Rule identity and all records include the stable environment ID. **Global** means all eligible projects and no-project chats in that environment, including projects created later. It does not automatically authorize another environment.

The project/chat catalog syncs automatically from T3: bootstrap from an authoritative snapshot, then consume existing project/thread lifecycle events and periodically reconcile. New projects and chats appear without a registration step. Renames update display labels; stable environment/project/thread IDs preserve bindings. Global rules automatically apply to new eligible projects and chats, with no additional scope-approval prompt. A new thread's initial request is observed as fresh work, not skipped as historical bootstrap.

Project rules bind to the stable project ID, never the title, path or branch. They add to global rules. A project can **Mute here** on a global rule; that does not edit the global text or affect other projects. Text overrides are outside the first version: create an additional project rule and explicitly mute the corresponding global rule instead. Deleted or inaccessible projects keep their configuration/history labeled Project unavailable; the supervisor never reattaches a rule to a new project with the same name.

The UI shows the effective rule set for each project, including the origin and any local mute, plus catalog freshness and connection state. No-project chats inherit global rules and get their own visible scope selector; the editor can create a rule restricted to that scope. T3 may represent these chats using real scratch-project IDs: identify them through authoritative catalog metadata, never by assuming `projectId=null` or matching titles/paths. A static owner mapping is acceptable only if step 1 proves that the complete scratch-project set is stable and enumerable. Otherwise each project lacking authoritative classification remains **Unclassified**, including newly discovered/recreated IDs. Send only rules whose effective scope and mute outcome are identical under both regular-project and no-project classifications; the rest show **Scope unavailable** with a Classify project action. Owner classification is bound to that exact ID, never inherited by a replacement. Unknown project identity yields Needs context.

Ordinary main threads and forks are eligible. Archived/deleted/settled threads, internal delegated work, imported/history-only activity and supervisor-control threads are excluded. Existing Telegram router and TEAMS exclusions remain initially, but the UI shows them explicitly rather than claiming “all chats” without qualification. Including other ordinary excluded chats is a later explicit owner choice; supervisor-control threads remain excluded to prevent self-observation.

The service stays available independently of any T3 chat while the Mac, Docker and T3 are running. A disconnected environment, expired credential, exhausted budget or unavailable model is shown as a monitoring gap. No uptime or detection-latency guarantee is implied.

## One monitor, with write capability

Extend the existing supervisor coordinator and its T3 connection with authorized read/operate access. There is no second independently configured monitor, second sending daemon, or nested reviewer chain. The same monitor cycle observes, evaluates and sends. Internal functions and persistent records keep those responsibilities understandable.

The monitor has one narrowly defined write action: `sendConfiguredGuidance(ruleId, evidenceRefs)`. It cannot choose another destination or compose a replacement message. The runtime binds the destination to the currently observed chat, loads the owner-configured text, checks eligibility, records delivery intent, and executes the write. The condition model's judgment chooses when to request this action; deterministic checks constrain what the action can do.

The model does not receive credentials or arbitrary shell/file/T3 settings tools. The existing questionnaire responder remains dedicated to exact native answers; it is not repurposed for general chat writes. Existing Telegram operations retain their current transport and durable identities. One UI exposes these workflows without merging their incompatible protocols or erasing their separate ledgers.

Prerequisite: verify that an existing writable T3 environment session can use supported activity reads and **steer-or-reject** with authoritative receipts/readback. The current read-only credential cannot do that. T3's MCP send accepts `threadId`, `message`, `mode` and `clientRequestId`; it does not document an expected run ID. Author-observed tool declarations/receipts expose message/run IDs, status, delivery and read-item source fields, but reviewers see different schema detail. Step 1 must establish the actual native response and provenance contract rather than treating these as guarantees. An optional expected-run field requires a mismatched-run rejection test: an extensible schema could silently ignore it. The supervisor's permission ceiling must cover the watched thread's runtime/interaction mode; a definite permission rejection becomes Not deliverable: permission. Settings shows which scopes can receive guidance. If the installed native session cannot satisfy the required behavior, Sending stays unavailable and Observe only remains possible. No T3 patch is the fallback. Only the constrained guidance sender receives the writable client, whose send mode is the literal `steer`; recap, questionnaire, model and UI code cannot call it directly.

## Effect ecosystem implementation

The existing backend uses `effect` and `@effect/platform-node` **4.0.1**. Keep its services, scopes, typed errors and persistence boundaries in Effect v4. Define the supervisor UI API and shared request/response schemas with `Schema` and `effect/http-api`; a browser contract contains public DTOs only, never server credentials or writable T3 clients.

The production frontend will use **Vite + React 19 + Effect Atom**, with `@effect/atom-react` **4.0.1** and Atom/AtomHttpApi from `effect/reactivity`. The installed v4 exports and the binding's published peer dependencies were checked: React 19, Effect ^4.0.1 and a compatible scheduler. This compatible baseline matches the existing backend, rather than claiming the latest patch. Resolve and pin aligned versions and a compatible lockfile during implementation; do not mix old `@effect-atom/*` packages or `/unstable/` import paths into v4. Atom, Reactivity and HttpApi APIs remain marked unstable, so keep the API/client integration behind a small adapter and test upgrades deliberately. [Official React binding](https://github.com/Effect-TS/effect/blob/main/packages/atom/react/README.md), [AtomHttpApi reference](https://effect.website/docs/v4/api/effect/reactivity/AtomHttpApi).

Use typed API atoms for rule/settings mutations and activity/catalog queries. AtomRegistry owns browser resource lifetimes and cancellation. A separate draft atom preserves unsaved edits while server/catalog atoms refresh; server compare-and-swap rejects stale submissions instead of overwriting them. Atom reactivity is process-local: authenticated server events explicitly invalidate/refetch affected browser queries, with reconnect resynchronization. It does not automatically propagate T3 changes across processes. The supervisor remains the authority for scopes, budgets, delivery and history. Serve the built Vite assets and API from the same authenticated supervisor origin; the dev proxy must preserve the owner session and CSRF checks. The adjacent standalone HTML is a UX mockup, not an implemented React application. No dependencies or production source are changed by this proposal.

Bind the Vite dev server to `127.0.0.1` with an explicit allowed-host list. Keep shared DTO modules free of server imports and verify the browser bundle excludes T3 clients and credential modules. Observe-only measurements include decisions already stale when classification finishes, so the freshness limit can be assessed against actual model latency.

## Observation and model judgment

The existing shell subscription is a wake hint, not proof that each streaming message was observed. Ongoing eligible threads also get bounded reconciliation reads, initially every five seconds with fair scheduling. Useful new activity triggers evaluation; token-by-token changes are coalesced. Capacity limits are visible. This intentionally trades coverage/cost and does not intercept tool execution.

Read visible owner instructions, the agent's public plans/messages and relevant allowlisted tool-call inputs, initially command lines rather than file-edit payloads. Rules may explicitly target owner-expressed or agent-expressed intents; the actor must be identifiable. Do not require access to hidden reasoning. Track stable item IDs **and locally computed content/revision hashes** by rereading an overlapping tail of the active run: a positional cursor alone can miss edits to an already known streaming item, and T3's summarized activity API does not provide a documented revision field. Use one evaluation at a time per thread. Store completed batches before advancing their checkpoint. Changes, deletions, rollback, gaps and incompatible schema versions invalidate affected evidence. A schema that cannot reveal a needed fact yields Needs context, rather than making up an event.

Context contains the latest owner request and explicit constraints, recent activity, relevant earlier evidence anchors, the pinned rule revision and a coverage/truncation description. It is bounded per thread and never borrows evidence from another thread or project. Missing history is visible. Searches for counter-evidence are bounded; absence in a truncated window is not proof of absence.

All conversation/file/tool material is evidence, not monitor instructions. Triggering evidence must identify the actor, the present situation and cited activity. Tool results can support a fact but never authorize rule edits, new recipients, permission changes or action execution. A user-role message alone is not proof of human ownership: require source metadata or a confirmed owner-origin Telegram routing identity. If provenance is unavailable, apparent owner cancellation/authorization yields Needs context and cannot authorize delivery. Injection attempts, unsupported origin, contradictory observations and insufficient evidence yield **Needs context**. Quoted examples, hypothetical situations and negation must not count as current intent.

The monitor produces `match`, `no_match` or `needs_context`, cited item IDs/revisions, a short evidence-grounded explanation and a suggested episode transition. Self-reported numeric confidence is not a calibrated probability and is not a hard gate. The runtime checks the pinned rule revision, evidence references and allowed transition before recording or sending anything. Monitoring has its own bounded model concurrency/token budget within the same service, so it cannot consume the recap/question capacity; rules applicable to one thread can share a bounded evaluation batch. Observe-only measurements determine useful defaults; 100k tokens/day in the prototype is an illustrative value, not a capacity claim.

Secret minimization/redaction is applied before model input and evidence retention. Redaction is best effort; the owner sees the configured model/provider and what kinds of activity leave the machine. Switching providers or widening scope never happens silently. Raw secrets and credentials are not audit-log fields.

## Delivery, stale intent and repeated reminders

Observe only records detections without sending. **Send guidance** is enabled once by the owner for the selected rule revision; no per-message owner approval is required. Editing name, condition, message or scope creates a new content revision in Observe only (or stays Paused), visibly canceling older uncommitted notices. No-op saves create no revision. Mode/pause/mute changes advance a **configuration generation** for dispatch cancellation, not the content revision or episode identity. Enabling/resuming Send starts a live watermark at the current head to filter fresh anchors; this does not rearm accepted episodes. Old zero-accepted observe-only episodes neither send a backlog nor suppress future fresh detections. Pausing cancels uncommitted guidance and continues observe-only evaluation within its budget; Settings distinguishes Pause guidance from Pause monitoring, which stops model cost as well. Recaps and native questions continue in either case.

Initially an outgoing notice requires an anchor changed within the last 60 seconds and after the applicable live watermark, plus a fresh destination-state read. The UI exposes this configurable age limit. After a connection/coverage gap, start at the current head; require new activity before sending rather than replaying the gap. A newly discovered thread's initial request qualifies only when authoritative creation time is after the watermark and within the age limit. Unsupported timestamps/freshness facts yield Needs context.

Before each send, re-read the destination's state and recent changes; verify environment/project, observed active run, rule revision/mode, exclusions, pause/mute, evidence freshness, existing requests and budget. A changed plan or later cancellation requires reevaluation. Then use a supervisor-local serialized commitment transaction, shared with rule/pause/mute/episode mutations: recheck configuration generation and claim one immutable outgoing operation. Configuration changes cancel everything that has not crossed this commitment boundary. A committed operation remains In flight or Uncertain and can complete even after Pause; the UI says so. The unavoidable race is limited to external T3 state changing after its fresh read, not to local stale authorization bypassing a pause or edit.

First version: request **steer-or-reject** only after verifying the observed run is still `running`. No `auto`, `queue`, idle wake, queue-to-promote workaround, restart, interruption or resumption. The transport spike must demonstrate explicit steer rejects, rather than starts or queues, for idle/preparing/starting/waiting/completed/queued threads and **running but not yet steerable** turns. A definite rejection records Detected, not delivered. An atomic expected-run condition is optional if the existing native API supports and enforces one. If run A ends and independently started B becomes steerable between read and steer, authoritative receipt/readback must show both the destination and that another message initiated B before recording **Delivered to a later run**. A notice queued as or initiating its own turn is **Transport contract violation**, not the permitted successor race; disable Sending for the entire environment until owner-triggered reverification. If the native API cannot establish that distinction, Sending stays unavailable.

Hold if the run is not `running`, or an authoritative activity/projection shows an open approval or native question. `t3_pending_request_list` explicitly omits approvals, so an empty list cannot establish approval clearance. Step 1 must verify approval visibility and that steering does not answer/resolve one; otherwise live sending stays unavailable for permission modes that can raise approvals. After a hold clears, use fresh evidence and reevaluate, never submit the notice as a native answer.

Bind every send-enabling proof to the authoritative T3 server/build and native-API version, connection identity and tested permission modes. Check this binding at connection establishment and before dispatch. A changed or unreadable previously known version invalidates proof and sets the environment to **Observe only (re-verification required)** until the applicable step-1 transport/approval/provenance subset passes again in a disposable thread. If T3 exposes no usable version identity, proofs are valid only for the uninterrupted verified connection; every restart or reconnect that could hide an upgrade requires reverification. Unknown current identity never reuses stale proof, and no queued notices are replayed after reverification.

The proof binding also includes the destination's provider instance/driver, model ID, runtime and interaction modes, control-relevant configuration fingerprint and separately versioned provider runtime/adapter. Step 1 covers each eligible provider/configuration; configurations may share proof only after demonstrated control-protocol equivalence, not an assumed provider-wide guarantee. An absent or outdated matching proof yields **Not deliverable: unverified provider**, while safe observation continues. Settings lists verified providers/configurations and their proof status. Credential/permission changes also invalidate the affected proof.

Connection identity means environment, endpoint and credential principal; an uninterrupted connection epoch is additionally required when no usable version identity exists. Pin dispatch to the verified connection: never transparently reconnect or retry. A lost connection before the dispatch-start marker aborts as Not deliverable; after the marker it remains Delivery uncertain. Native read-safety and reconciliation/normalization proofs are bound to the relevant current identities too. While drift is unresolved, use only already established side-effect-free read paths; suspend any unverified read path and show a coverage gap rather than assuming observation is harmless. Current proofs are required to classify readback as Visible or Reconciled: no effect; old unknown effects remain durable across upgrades.

The owner starts initial verification or reverification from Settings; automatic reconnect only pauses affected sending and reports the gap. Verification threads are explicitly excluded from monitoring, recaps and Telegram, and archived after their result is recorded. They never invoke the model detector, send Telegram messages or answer approvals. A successful verification advances the applicable live watermark to the current head, preserving accepted episodes and unknown effects, so it sends no accumulated backlog. If there is no version identity, frequent reconnects can reduce live availability; the UI must explain that limitation.

Record the exact configured body with a fixed provenance header containing a unique non-model **notice ID** before dispatch. The ID is derived with a server-held keyed hash from the immutable delivery identity; it is stable across reconciliation and distinct between notices. Preview uses a visibly illustrative ID until an actual notice exists. A receipt means **Accepted by T3**; **Visible in chat** requires readback tied to that receipt's message ID or equivalent authoritative dispatch correlation, notice ID and exact bytes under only the documented text normalization proven in step 1. Preserve original bytes; do not use fuzzy text matching. A same-text older notice cannot confirm a newer one. An identical pasted header/body alone is not authoritative source proof. If origin/receipt correlation cannot be recovered, keep the notice uncertain; never label a fake header as owner consent or a confirmed supervisor effect. **Followed** is never inferred from acceptance. The model cannot add text to the configured body. Display the entire outgoing message in preview.

Each rule/thread has a durable intent episode. Its ID derives from environment, thread, logical rule and first fresh anchor; a unique constraint permits only one open episode per environment/thread/logical rule, independently of mode, watermark and configuration generation. A per-thread evaluation lock prevents hint/reconciliation races. Delivery state is separate from episode state. Repeated plans, acknowledgements and new batches do not create another episode. Accepted episodes persist across pause/resume, mute/unmute, mode changes and content edits. A watermark change can supersede only zero-accepted episodes without unresolved effects. An episode with zero accepted notices may use a newer, fresh revalidated anchor in a running turn to deliver once; a held/throttled/not-delivered outcome does not silence the thread permanently. A pre-activation observe-only episode cannot suppress live delivery.

A cooldown expiring, a model no-match caused by missing data, or a restart does not rearm an accepted episode. Close on cited cancellation/resolution, settled/archived/deleted thread, a distinct new situation with a cited object (for example a different PR), or an explicit owner reset. The runtime checks that the authoritative cited object ID belongs to this context and differs from the episode's stored object ID; model wording alone cannot create a new-object transition. A changed condition alone does not resend into already-notified threads: use a cited new situation or an explicit reset, with fresh evidence. Delivered episodes remain historical evidence; unresolved delivery effects survive any edit/reset/prune. Activity shows open episodes and a Reset action, which never erases an uncertain send or manufactures a replacement identity. Step 1 establishes whether new activity clears auto-settlement; eligibility follows authoritative state rather than permanently excluding a previously settled chat.

At most one accepted notice per episode. A delivery attempt has a stable identity including environment, thread, logical rule ID, episode ID and attempt ordinal; the job pins rule revision, observed run and observation revision. Commit at most one dispatch per identity. Write a durable **dispatch started** marker immediately before the network call. After restart, a committed row without that marker becomes Not delivered (restart); never dispatch it. A marked row with an unknown effect becomes **Delivery uncertain**, including a crash between marker and call. Reconcile receipts/readback under the original key; no automatic redispatch in the first version, even with the same key.

An authoritative rejection/no-effect proof produces **Reconciled: no effect** and permits a new attempt only against a new fresh anchor. Step 1 must document which receipt lookup, retention window or bounded native execution contract can establish that proof; absent readback alone cannot. Unknown effects block further attempts for that rule/thread across edits, resets and activations. If no authoritative reconciliation is possible, offer the owner **Accept uncertainty**: explain that the old notice might have arrived or still arrive and future guidance could duplicate it. This explicit action preserves its identity/bytes and the uncertainty history, never retries the old operation, but permits a future fresh episode. It is unavailable for existing Telegram/native-answer workflows. Acknowledged receipts prove transport effects, not agent compliance.

Supervisor-authored message identities are recorded and excluded from trigger evidence. An uncorrelated possible notice is quarantined as uncertain origin, not promoted to owner instruction. A fake header typed by a user is not treated as supervisor provenance. A worker quoting/acknowledging guidance does not itself rearm the rule. A per-thread limit, initially three notices/hour across all rules, prevents overlapping rules from flooding the chat. Further eligible attempts at that limit become Throttled; repeated detections within an already-notified episode remain suppressed rather than consuming another slot. Throttled work must be freshly revalidated before later delivery. Resume starts at the current head and never sends accumulated reminders. Unknown effects are never hidden by this watermark.

Recap contexts label correlated notices as Supervisor guidance, never as the originating owner's request. A notice or an acknowledgement alone cannot create recap eligibility; substantive work continues through the existing qualification policy. Preserve the durable originating Telegram dispatch ID and exact final-answer routing even if guidance arrives in the same run. Do not synthesize another Telegram-origin request or rewrite its answer. The audit may show that guidance was present, without claiming that the human issued it.

## UI and operational history

The application belongs to the supervisor, served locally on a separately configured loopback UI port, with the existing health endpoint preserved. The operator can open it without launching a T3 conversation. Desktop and phone-width layouts share the same interactions; remote network exposure/authentication is a separate later choice.

Primary areas:

1. **Rules:** automatically synced global/project/no-project selector, effective inherited rules, Mute here, Add rule and edit. The editor separates the detection condition from the exact outgoing message, previews provenance, and offers Paused / Observe only / Send guidance. Unsaved changes remain visible; leaving the editor asks whether to discard them. Selecting the current view is a no-op. Creating from a project/no-project view preselects that scope explicitly.
2. **Activity:** chronological guidance decisions with chat/project, trigger evidence, pinned rule revision, explanation and delivery state. Filters include matched, Needs context, throttled, stale and uncertain. Pause this rule, mute here and “This was wrong” are contextual actions. Feedback records an assessment; it does not train a model or mutate a rule without an owner edit.
3. **Telegram:** existing recap decisions (including skipped), exact-answer delivery, reply routing, native questions and cleanup. Explain why a routine turn was skipped and distinguish dispatched, accepted, confirmed sent, unknown and cleanup pending. Link the originating T3 thread and preserve original update/message/request/run identities. An accepted Telegram route is not task completion; accepted native input is not proof the provider resumed; HTTP 202 or healthy transport is not delivery proof. Use **Cleanup uncertain** for an unconfirmed deletion, rather than implying answer delivery failed.
4. **Settings:** one connection with read/write readiness, detector model, bounded model/observation budgets, evidence retention, explicit excluded chats and a global pause. Completion recaps and questionnaire health remain visible even when guidance is paused.

**Test a rule** uses synthetic or explicitly selected historical evidence in a send-disabled execution path. It shows match/no-match/Needs context, exact cited material and the message that would be sent. A replay never writes to T3 or Telegram. Arbitrary edits must be tested by the real classifier in the implemented product; the prototype's canned scenarios are labeled fixture demonstrations, not semantic validation.

The dashboard must never imply that an unchanged rule is healthy just because no matches occurred. Show the last observed activity, last evaluation, observation/model lag, budget-paused/unavailable states and coverage gaps. Detected-but-not-delivered rows remain explainable. Pause all guidance must work without waiting for a model.

Recap silence currently removes pending raw context and keeps a deduplication identity, not an explanatory history row. First durably pin the classification result on its pending source record. Add a minimal decision record **in the same source-store transaction** as retaining identity/removing pending context; if that transaction fails, work stays pending and retries the stored decision, not Luna classification or external effects. If initial decision persistence fails, classification may need to run again; no effect or final classification is claimed until stored. Record correlation ID, workflow kind, environment/thread/run IDs, timestamp, enum outcome/reason, attempt identity and known receipt IDs. Native/input/cleanup audit entries belong to the transaction in their existing store, then feed the unified read view idempotently; there is no fictitious atomic transaction across independent SQLite files. A view-projection failure never causes external sends to repeat. Retention prunes bounded audit projections without deleting deduplication or uncertain-effect identities. Existing skipped history cannot be reconstructed and is labeled unavailable; do not fabricate reasons. Native questions, delivery and reply-cleanup retain their existing databases. Unified history reads bounded projections of those stores and new audit events, never silently mutating them.

Use native labeled controls, visible focus, 48px main touch targets, a single-column mobile editor, accessible status announcements and no hover-only actions. Escape closes dialogs; focus returns to the triggering control. Text is rendered as text, not HTML.

Delivery states stay specific to the effect. Guidance has Observe only, Held, Throttled, Stale, Cancelled by edit, Detected not delivered (including restart), Not deliverable (with reason), In flight, Accepted by T3, Visible in chat, Delivered to a later run, Delivery uncertain, Reconciled: no effect, Uncertainty accepted by owner and Transport contract violation. Recaps have Skipped (enum reason), Pending, In flight, Confirmed sent (Telegram receipt) and Delivery uncertain. Native question history keeps answer acceptance, provider state and card/reply cleanup as separate fields: Cleanup uncertain is not a failed answer. There is no single “success” badge inferred from process health, an HTTP response or a classifier match. These state labels describe the underlying source records, not replacement state machines for existing ledgers.

## Data and control surface

Add monitor/configuration and decision tables in a supervisor-owned store, bound to the environment. Existing completion, input and reply-cleanup ledgers remain intact. Principal records: immutable rule revisions; project mutes; observed item revisions; evaluation/coverage records; intent episodes; guidance outbox/receipts; minimal cross-workflow audit entries; owner feedback. Editing uses compare-and-swap tokens covering content revision **and configuration generation**, so another tab's mode-only pause cannot be overwritten by a stale save.

Suggested retention: ephemeral model windows; redacted evidence/explanations 24 hours; enum-only decision/delivery metadata 30 days; bounded payload-free identities beyond pruning to prevent replay. Exact uncertain outgoing bytes survive until reconciled. The UI labels evidence that has expired, and metadata-only rows do not pretend to contain a full transcript. Logs, spans and telemetry contain IDs, enum outcomes, counts and durations only: no chat titles, prompts, raw tool inputs, model output, evidence snippets or message bodies. Sanitize exception causes before logging; preserve bounded container log rotation. Free-text recap skip reasons use the short-lived evidence policy, not long-lived metadata. Size limits surface capacity exhaustion instead of deleting unknown effects.

Configuration/audit routes use an owner session established by a single-use locally generated bootstrap code, with an HttpOnly SameSite=Strict cookie, idle expiry and logout. An owner-invoked local command obtains the short-lived code through a restrictive-permission local file and prints it directly to the owner's terminal; never put it in container logs or telemetry. Bind the UI inside the container as needed, but publish its port on the host's `127.0.0.1` only; Docker loopback inside the container is not host loopback. Cookies are not isolated by port: enforce exact same-origin/Host checks and CSRF tokens for mutations, including requests without Origin, rather than relying on SameSite to isolate other local services. T3 credentials remain mounted server-side and never reach browser JavaScript. Read-only history routes still require authentication because chat titles and delivery records are private. Use a restrictive CSP in the actual application. Phone-width layout is supported; actual phone access requires later explicit remote-exposure/authentication work. The standalone prototype has no network or credential access.

Only the trusted owner UI can create/enable rules or change model, scope, pauses and permissions. Chats and detected content cannot make those mutations. UI settings are saved once; normal monitoring and guidance require no repeated approvals. Existing operational replay, uncertain-delivery reconciliation and cleanup retain their authorized contracts. The guidance-only Accept uncertainty action is a recorded risk acknowledgement, not a resend button or a claim of no effect.

## Delivery plan and evidence required

1. **Transport feasibility:** in a disposable ordinary T3 thread, verify automatic project/thread catalog changes and classification of new/recreated scratch IDs; settlement/reactivation; streaming updates with overlapping reads/local hashes; owner/agent/relay/monitor provenance; waiting/approval visibility; steer-or-reject including queued and running-but-not-steerable states; actual receipt/message/run IDs, text normalization, durable correlation/retention and no-effect determinability. Prove read operations have no workflow side effects: MCP terminal-child reads can acknowledge completion, so do not assume the native read adapter is equivalent. Test the independently started successor-run race separately from forbidden notice-initiated/queued turns; the latter disable Sending. Negatively test any optional run condition. Do not use queue-to-promote to fake run pinning. Do not test using an implementation chat or send to Andrea's Telegram. If a required native fact is unsupported, expose the specific unavailable scope/mode rather than changing T3. The prototype has not performed this spike.
2. **Unified UI/history:** add owner-authenticated rules/settings and read-only recap/Telegram views, plus new minimal explanatory audit records. Preserve completion and native-input behavior.
3. **Observe only:** evaluate global/project rules against ongoing activity with no writes; exercise quotes, cancellation, history loss, fairness and costs. Gather false-positive feedback.
4. **Guidance:** enable same-cycle configured sends after transport verification. Add episodes, scope/freshness checks, durable uncertainty and immediate pause. No change to T3.

Meaningful regression/acceptance cases: automatic project/thread creation and catalog reconnect with no historical replay; global rules on a newly discovered project and a real no-project chat; project rename/delete/recreate/move/mute; concurrent hint/reconciliation episode creation; unsent observe-only/held/throttled episodes promoted against fresh live evidence; duplicate evidence across batches and restart; edits to a known streaming item; missing history/review evidence; negation/quotes/injection; current assistant intent versus human instructions; fake provenance and acknowledgements; same-text notices in different episodes; rule edit/pause at either side of local dispatch commitment; run ending/changing during send and successor-run labeling; open native approval/question; crash before/after dispatch with uncertain acknowledgements; rule edit/reset/prune with an unresolved send; notice arrival in an ordinary recap and a Telegram-origin exact-answer run; transactional skipped-recap audit failure; exact answer multipart order; native cleanup uncertainty; expired evidence; sanitized logs/telemetry with planted secret sentinels; model/connection/budget gaps; disconnected multi-tab edit; keyboard/mobile rule edit, current-tab no-op and exact preview. Run all existing supervisor tests before activating implementation.

Include pause/resume and mute/unmute after accepted guidance; content edits without implicit rearming; unclassified replacement scratch projects with conflicting mutes; committed-without-marker versus marked-before-call crashes; authoritative no-effect proof versus owner-accepted uncertainty; forbidden queue/start detected as a transport violation; cross-tab mode-only CAS; browser event reconnect and draft preservation; whitespace-validation recovery and keyboard focus. The native spike, detector measurements and production Effect frontend tests remain implementation work.

## Decision boundary

This proposal deliberately chooses one local environment, global inheritance with explicit project mutes, an integrated monitor with a constrained write action, observe-only defaults and steer-only live delivery. Multi-environment federation, child-thread monitoring, automatic restarts, hard vetoes, automatic rule rewriting and exposing the UI remotely are later work. No runtime or credential changes are included in this proposal.
